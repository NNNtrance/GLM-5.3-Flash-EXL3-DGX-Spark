# KL health check against the official reference — the measurement that found the router bias (7–8 October 2026)

**Applies to: TP=3, the main (vLLM `main`) stack.** The check is a method, not a setting: it compares the
engine's next-token distributions with the checkpoint author's own implementation on the same text. It found
the defect described in the README's correctness notice, measured the fix, and was re-run on the
production build.

The question it answers is narrower than "is the model good": **does this engine compute the same
function as the reference implementation of this checkpoint, to within the noise that two runs of either
implementation already show?** It cannot say which of the two is closer to the unquantized BF16 model; there
is no BF16 run in this repository's evidence (see §9).

## 1. The headline: assistant-token KL, three builds

Assistant tokens are the positions inside the model's own turns — the only region where both
implementations behave stably (§5 explains why the all-positions column is not the headline).

|---|---|---|---|---|---|

| **Pre-fix** (`a4f`) | **0.1033** / 0.00779 | 90.2 % | 2.288 | 1.754 / 0.265 | 63.8 % |
| **Bias-fix** (`a4g`), run 1 / run 2 | **0.00841** / 0.00048 · 0.00808 | 97.6 % · 97.8 % | **2.222** | 0.326 / 0.0190 | 85.8 % |
| **Production** (`a4i`), run 1 | **0.00828** / 0.00047 | 97.9 % | — | 0.334 / 0.0192 | 85.8 % |
| Production, booted at 0.85 for the memory trial | 0.00806 / 0.00047 | 97.9 % | — | 0.332 / 0.0191 | 86.1 % |

Reference perplexity on the same assistant tokens: **2.224** `[measured-here]`. The bias-fix build's 2.222
is level with it; the pre-fix build's 2.288 was worse on every text (Turkish 3.15 against 3.00, long

KL was Turkish 0.161, English 0.134, long 0.149, reasoning 0.105, tool-call 0.059, code 0.034, against
floors of 0.004–0.012.

For orientation only: the checkpoint card reports the 4.05 bpw quantization against BF16 at KL mean
**0.0345** / median **0.00312** on model-generated in-domain text, with its own noise floor at
0.01378 / 0.00119 `[reported]`. Different text, so these are not our targets and not a pass line; they are
the scale of quantization loss. The pre-fix engine added about 3× that loss on top of it.

## 3. The cause, and how it was proved

An independent computation of the **official** MoE formula (sigmoid scores plus
`e_score_correction_bias` for selection, renormalise, × 2.5, clamp at 10, plus the shared expert) in fp32 on
the engine's own layer-3 inputs, with each expert's weights decoded by the reference's own format decoder:

| Comparison (96 positions, median) | Magnitude ratio | Cosine | Relative difference |
|---|---|---|---|
| exllamav3 routed output vs official formula | **1.0000** | 0.9999998 | 0.07 % |
| **Engine** routed output vs official formula | **0.771** (p10 0.66, p90 0.91) | 0.993 | 28 % |
| Engine routed output vs official formula **using the engine's own (bias-free) selection** | 1.0000 | 0.99999 | 0.43 % |

The expert kernels were right; **which experts were selected** was wrong. The engine's router bias was
exactly zero (maximum 0.0, in layers 3, 4 and 5), the checkpoint tensor is fp32 with mean **7.76**, and the
router logits themselves matched the checkpoint's to 4e-6. Eight-expert sets: the engine matched the
official selection at **0 of 96** positions (about 3 of 8 experts in common); exllamav3 matched at 97.9 %
(the remainder are ties and fp16 bias rounding).

The code chain, in the pinned tree: `Glm5NextMoE` creates the bias as `nn.Parameter(torch.empty(288))` and
hands the same object to the MoE factory; `RoutedExperts.__init__` registers it as a direct parameter of the
layer; `Exl3MoEMethod.create_weights` then iterates **all** of the layer's direct parameters and replaces
every one's `weight_loader` with the plugin's expert-aware loader; during loading, the bias arrives without
expert arguments and that loader declines it silently; vLLM's "weights not loaded" check is off for
quantized models. The tensor stays at `torch.empty`'s zero. No error, no warning.

A measurement-instrument lesson recorded because it nearly produced a wrong report: the first version of
the official-formula computation took its expert selection from the engine under test, and so showed the
reference "inflating the routed output 1.29×". Rebuilding the selection from the checkpoint's own bias
reversed the table. That intermediate verdict was never published; the rule it taught is that **a ruler may
not take its inputs from the thing it measures**.

## 4. The fix and its measured effect

Fix (build `a4g`, `cuda-exl3` `1451b1a`): the loader is installed only on the plugin's own eight parameters
(w13/w2 × trellis, suh, svh, mul1); a foreign parameter arriving without expert arguments goes to vLLM's
default loader instead of being dropped; and a **fail-closed boot gate** in `process_weights_after_loading`
refuses to start if any expert tensor was never written, or if a layer's router bias is all-zero, contains
NaN/Inf, or differs **at the bit level** from the checkpoint's. It logs
`[HAREM-MOE-KAPI] GECTI <layer>: N/N expert tensors written; router bias = checkpoint ... (288 experts, max diff 0)`
once per layer: **42/42 on all three ranks** at every boot since. Unit tests: 14 new, **14/14** green, and
**12 of 14 red** against the previous `moe.py` (the two that stay green are deliberate regression guards).
Full image suite 588/588 on the GB10 (620/620 on the production build).

| Measure (TP=1 truncated model, layer 3) | Before | After |
|---|---|---|
| MoE contribution, engine / reference (ratio / cosine) | 0.722 / 0.9892 | **1.000 / 1.0000** |
| Block-3 difference to reference | 0.302 | 4.98e-3 |
| Expert selection equals official | 0 / 96 | **96 / 96** |
| Routed output / official formula | 0.771 | 0.9999 |

TP=3 full model after the fix (§1): assistant KL 0.103 → **0.0084**, i.e. down to the engine's own repeat
floor (0.0081); top-1 90.2 % → 97.6 %; perplexity 2.288 → 2.222 against the reference's 2.224. Boot gate
passes: 3 ranks × 42 layers, 1,152 of 1,152 expert tensors written per layer (96 local experts × 12), max difference 0, on both the
normal-load/dump boot (380 s) and the fast-load LOAD boot (171 s, 6,456 tensors restored, verified).

**Layer curve after the fix:** 41 of 45 layers within 5× of the reference-jitter curve, **none above 10×**
(before: layer 3 at 152×). Four layers sit just above 5× (layers 3, 18, 25, 26: 5.2–5.7×) with attention
contributions at ratio 1.0–1.03 and MoE contributions at ratio 0.99–1.12 and cosine ≥ 0.9995. Measured explanation:
with the bias loaded, expert selection has more near-ties — the median gap between the 8th and 9th expert's
selection key is 3.0e-3 (6.2e-3 without the bias), and 24 % of positions sit under 1e-3 (11 % without) — so
small numeric differences flip a selection more often; the reference itself departs from the official
selection at 2.1 % of positions for the same reason (fp16 routing) `[measured-here]`. The deep-layer
differences (layers 35–44, 5.5e-2–7.6e-2) are at the engine's own repeat level measured before the fix
(7.5e-2–7.9e-2); the repeat curve was not re-measured on the fixed build.

### Padding does not shift heads

The checkpoint is padded at TP=3 (attention and KDA heads 64 → 66, shared expert 2,048 → 2,304, vocabulary
154,880 → 155,136). Three independent pieces of evidence say the padding is not displacing real data:

1. **Code.** The pad is appended at the right end of the tensor, then the rank slice is cut: ranks 0 and 1
   hold real heads 0–21 and 22–43, rank 2 holds 44–63 plus two zero heads. In the boot log all **17**
   distinct `HAREM-TP3 pad` lines are on rank 2 only, all "slice N @ 2N", all trailing.
2. **The corrected layer curve** above: a head shift would put the attention cosine near 0.5, not ≥ 0.946
   (layers 1–44).
3. **TP=1 against TP=3**, same positions, layers 0–5 (no padding at TP=1): differences ≤ 1.1e-2 and
   cosine ≥ 0.9987 for KDA, MLA, dense MLP, MoE and the shared expert. No jump.

## 5. Why the all-positions column is not the headline

Both implementations are wildly uncertain at **user and tool-result tokens** (the model rarely has to
predict them): perplexity there is 8.7–1,019 for the reference and 6.1–602 for the engine, on hard-wrapped
English prose after a Turkish instruction and on JSON tool output. Those positions dominate the all-positions
mean and amplify any tiny numeric difference 500× over 45 layers; the reference shows the same
amplification against its own bf16-jittered copy (0.1–0.6 on non-assistant rows against 0.003–0.012 on
assistant rows). So the reported all-positions floor (0.281) is large, and a correct engine sits at it
(1.16× on the mean after the fix). **Use the assistant-token column.** Per text, assistant-token KL after
the fix (reference vs engine, floor in brackets): Turkish 0.0128 (0.0089), English 0.0056 (0.0042), code
0.0028 (0.0027), tool-call 0.0054 (0.0045), reasoning 0.0123 (0.0103), long 0.0141 (0.0117).

Other pieces that were checked and are clean on the fixed build:

| Check | Result |
|---|---|
| Sparse versus dense region (positions ≥ 2,048 against under) | mean 0.451 against 0.176 — 2.6×, inside the pre-registered 3× limit; ratio to each region's own floor 1.14× / 1.07× |
| Prefix-cache path (3,547 positions after a 6,656-token hit = 2 × 3,328) | KL(run 1 ‖ cached run) is 1.04× the engine's own repeat on the same rows; pre-fix it was 1.00× (0.2406 against 0.2407) |
| Text-by-text ratio to floor | 0.68–1.15× |
| Teacher-forced loss on the true next token (assistant rows) | mean ΔNLL to reference 0.063 (floor 0.059–0.064); rows with \|Δ\| > 0.5: 2.3 % (floor 2.3–2.4 %); pre-fix 0.248 and 15.7 % |

## 6. The routed-expert SwiGLU clamp (production build, `448f1d6`)

The official model clamps SwiGLU inside every expert (gate ≤ 10, up in [−10, 10]); the `cuda-exl3` fused
GLU did not clamp the **routed** experts (the shared expert and dense MLPs did). `448f1d6` adds the clamp.
It was kept in the production build because it is the model's definition, **not because it was seen to
matter**.

| Check | Result |
|---|---|
| Is it on | 42/42 layers on all three ranks log `swiglu_limit 10 (routed experts clamp)`; the bias-fix build logs none (negative control) `[measured-here]` |
| Assistant KL to reference | **0.00828** against the bias-fix build's two measurements 0.00841 and 0.00808 — inside its band |
| Does the engine move toward the *clamped* reference? | **No trace of it.** All-positions KL to the clamped reference 0.3343 is *higher* than to the unclamped one (0.3081); the bias-fix build shows the same direction (0.3255 against 0.3021). The bias-fix → production difference (0.287) is the size of the engine's own repeat difference (0.281) |
| Layer 3 | clamp inactive: largest gate 9.88, 3e-6 of up-values beyond 10 |
| Speed, same session, each arm after its own triple reboot | one-user step **75.84 → 74.44 ms (−1.85 %)** (one step is 0.9 %), four-user **160.25 → 160.26 (+0.01 %)**; fast-mode C1 74.9 → 74.9, C4 157.3 → 158.4 (+0.67 %); memory band 241.3 → 241.1 GB/s (−0.08 %) |
| KV pool | 4,656,675 → 4,675,749 tokens at 0.75 (+0.4 %); boot 186 → 170 s |
| Teacher-forced lossless check (17 prompts × 256 greedy drafted tokens = 4,352, re-scored in one target pass; counts positions where the target's argmax equals the generated token) | 99.20 % agreement, 13 large-margin divergences, against 98.90 % and 17 for the bias-fix control run in the same session |

**What this cost:** nothing measurable — a speed difference inside measurement resolution, a KV pool within
boot-to-boot spread, no boot-time change. **What it gained:** nothing measurable on these six texts either.
The clamp's effect inside the *reference itself* on these texts is also at the jitter level (KL between the
clamped and unclamped reference 0.251 over all positions against a jitter floor of 0.281; assistant tokens
0.0061 against 0.0067), which is why no engine-side trace was expected. Where the clamp matters, if anywhere,
is the rare activation beyond 10, which these texts apparently seldom produce; we did not build a text set
that does. That is the open item. (Only the **routed** experts were unclamped in the plugin: the shared
expert and the dense MLPs already clamped.)

Build side: `tests` 620/620 in the image (31 GLU tests and 16 clamp tests among them); the same commit adds
`CUDA_EXL3_GEMM_TUNE_REPS` and `CUDA_EXL3_GEMM_TUNE_VERBOSE`, both off by default. With verbose on, the GEMM
tuner's pick differed between ranks in **25 of 113** shapes (mostly ties such as 16.3 against 16.4 µs) and
departed from the heuristic's choice in 61/61/64 shapes per rank — a source of boot-to-boot variation, not
tuned further.

## 7. Pre-registration, and where the rules were wrong

The verdict rule was written into the log **before any data** (16:32), and the thresholds were not changed
afterwards:

- *Healthy* needed all of: engine-versus-no-clamp-reference KL ≤ 2× the larger floor (mean and median); KL
  median ≤ 0.00312; top-1 ≥ 98 %; no text or region above 3× the overall mean; prefix path ≤ 2× the repeat.
- *Problem* if any of: KL mean ≥ 0.0345; any text or region ≥ 5× its own floor; top-1 < 95 %.

**Pre-fix result: PROBLEM** — all three problem conditions fired, and the rule was right. The check had
been designed to find a defect we did not know about, and it did.

**Post-fix result by the same literal rule: still PROBLEM.** Two *absolute* thresholds (KL mean 0.0345, top-1
95 %/98 %) are exceeded by the **reference's own jittered copy** on this text set (mean 0.281, top-1
86.3 %), because of the user/tool-content volatility of §5. The rule would flag the reference itself. We did
not reverse the literal verdict and we did not quietly drop the thresholds. What we report beside it:

| Pre-registered *relative* condition | After the fix |
|---|---|
| KL to no-clamp reference ≤ 2× larger floor, mean and median | 0.302 ≤ 0.562 and 0.0185 ≤ 0.0364 — pass |
| no text or region ≥ 5× its floor | pre-fix: seven of eight breakdowns fired (5.8×–12.6×; tool-call 4.5×); after: **none**, 0.68–1.15× |
| breakdown mean ≤ 3× overall | pass |
| prefix path ≤ 2× repeat | pass (1.04×) |

and, as *information* (not pre-registered as a gate, read after the data): the assistant-token subset passes
the absolute mean (0.0084 < 0.0345) and median (0.00048 ≤ 0.00312) thresholds and misses only the 98 %
top-1 line (97.6 %) — which the reference's own jitter (97.3 %) also misses.

For the production-build re-check the corrected rule *was* written before its data: assistant KL must be at
most **1.08 × the larger of the two bias-fix-build measurements (= 0.00908)**, and the rule was first applied
to the baseline against itself (a negative control: it must not "win" against its own repeat). That
discipline is the lasting change. Two further rule corrections for that chain were also made before data:
the drafted-run agreement criterion was changed from an absolute count to a **ratio** (the draft-schedule
chain had shown an absolute count penalises an arm that happens to generate fewer tokens;
[draft-schedule.md](draft-schedule.md)), and the speed-band validity check now uses **each arm's own
post-reboot bandwidth probe** rather than one probe around both arms ([bandwidth-fragmentation.md](bandwidth-fragmentation.md)).
The production build passed all four pre-registered gates on the corrected rules (boot gate and clamp log
42 × 3; KL 0.00828 ≤ 0.00908; agreement 99.20 % ≥ 98.40 %, 13 large divergences ≤ 34; step-time change
inside ±2 %).

## 8. What this cost

- **Speed**, the price of reading the correct experts: decode steps **+11 % (one user) to +20 % (four)**
  against the same software without the bias — see [speed-map.md](speed-map.md) §1. This is not a defect of
  the fix; the old speed came partly from the wrong selection.
- **Memory, boot:** a 288-float tensor per MoE layer; the gate adds one log line per layer. Fast-load boot
  was 169–186 s on the bias-fix and production builds (the pre-fix build's first LOAD boot read 252 s, 49 s
  of which was a compile-time skew between nodes, since fixed); the gate's own share was not isolated.
- **Engineering:** one 2–3 line change in `create_weights`, one gate, one rebuilt image per fix.

## 9. What we tried and rejected, open problems, retracted

**Rejected as the cause** (each measured): fp8 MLA KV cache `[measured-here]`; FlashKDA `[measured-here]`;
sparse attention or chunk boundaries (short texts already failed) `[measured-here]`; the TP=3 + EP merge
(TP=1 reproduced it) `[measured-here]`; head/row padding shift (three-way evidence, §4) `[measured-here]`;
the known-missing SwiGLU clamp (closing it moved the pre-fix KL by 2 %: 1.754 → 1.723) `[measured-here]`.

**Open problems**

- **No BF16 reference.** The evidence that the reference is the closer of the two is indirect: it matches an
  independent computation of the official formula to 1.0000, and its perplexity on true assistant tokens is
  equal to or better than the engine's in every text. A BF16 run would settle it.
- The absolute rule thresholds above are unreachable on this text set; a model-generated, in-domain text
  (as the card used) would let them be used as written.
- Six texts, 21 k positions, one language mix: a regression test, not a benchmark.
- The deep-layer repeat curve was not re-measured after the fix.
- The same defect is in the upstream pull-request copy of the plugin (offered upstream as
  [Zeuss5/cuda-exl3#8](https://github.com/Zeuss5/cuda-exl3/pull/8); not waiting on it).

**Retracted by this work:** every quality figure measured on the pre-fix routing — see the README's
correctness notice and [`docs/11`](../../docs/11-open-issues.md) §1.15; replaced for the quantity measured
here by §1 above, and *not* replaced for the benchmarks (see [quality-gates.md](quality-gates.md)).
