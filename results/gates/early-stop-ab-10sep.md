# Early-stop A/B: speculative decoding on and off, 24 long-form prompts at temperature 1.0 (10 September 2026)

**Why.** Issue #1 reports intermittent premature end-of-turn on long-form generation (`finish_reason = stop` at implausibly short lengths, temperature 1.0 / top_p 0.95), worse in warm sessions, persisting after the reasoning-retention fix, and asks whether the DFlash2 port's verification accepts a draft-proposed EOS too easily. The reporter could no longer run the A/B; we ran it.

**What the code says first.** In the image the verifier (`vllm/v1/worker/gpu/spec_decode/rejection_sampler.py`, `_verify`) passes the target logits through `apply_sampling_params`, which applies logit bias, penalties, the thinking budget, temperature, min_p and then top-k/top-p, before `rejection_sample`. So the target distribution used for acceptance is the same processed distribution plain sampling uses; the "verification ignores top_p, so tail tokens such as EOS become samplable" explanation is out. There is no EOS-specific code in the verifier, as the reporter found; EOS is recognised after sampling, by the engine, identically with and without speculation. The draft samples with Gumbel-noised argmax at the request temperature and caches its logits, and the rejection kernel scales those cached logits by the same temperature (`rejection_sampler_utils.py`). Whether the accept path is exact in practice is what the measurement below is for.

**Setup** `[measured-here]`. Production configuration 13 (`5da7f5d`, K-pool tail fix and prefix-hit fix in, vision on, `gpu_memory_utilization` 0.88), `reasoning_effort: low` (the reporter's setting), temperature 1.0, top_p 0.95, no penalties, `max_tokens` 4,096, four concurrent requests. 24 prompts that each demand a long output: eight technical articles and four structured documents at ≥ 2,500 words, six short stories at ≥ 2,500 words, six Python modules at ≥ 400 lines (≥ 1,800 words). "Early stop" is `finish_reason = stop` with fewer than 40 % of the requested words. Arm A is the production engine (DFlash2, k=7); arm B is the same engine restarted with `SPEC_METHOD=none`, nothing else changed. The 4,096 cap was chosen after a first pass at 8,192 showed the model writing about 8,000 tokens (5,000+ words) per prompt; a cap does not hide an early stop, it only bounds the run.

| Arm | n | early stops | `finish_reason` | median words | min words | median wall time per request (4 concurrent) |
|---|---:|---:|---|---:|---:|---|
| A: DFlash2 k=7 on (production) | 24 | **0** | `length` 24 | 2720 | 1549 | 204 s / ~82.8 tok/s |
| B: speculative decoding off | 24 | **0** | `length` 24 | 2631 | 1538 | 204 s / ~81.0 tok/s |

**Verdict.** Zero early stops in either arm, 48 requests: every request ran to the 4,096-token cap with coherent text at the cut, on and off. At this sample size the drafter's accept path shows no EOS bias at temperature 1.0 / top_p 0.95, which is what the code reading predicted. The early stops reported in issue #1 came from a window that predates the K-pool tail fix; corrupted long-context KV state is the remaining and most mechanical candidate, and it is fixed in this configuration. The item is not closed: a single-turn A/B cannot reproduce a warm multi-turn session, which is what HELP-WANTED §14 asks for.

**A side note on speed.** Median wall time per request is the same in both arms (204 s against 203 s at four concurrent, 4,096 tokens each): on long-form English prose at this concurrency the k=7 drafter buys nothing, which is consistent with the low prose acceptance in docs/14 §9.10. The drafter earns its keep on code and at low concurrency; this workload is neither.
