# Production soak and regression gates on the xgrammar-backport boot (11 September 2026)

**Applies to: TP=3.** Nothing here was run on the TP=2 track `[not tested]`.

This page exists to answer one question asked in plain words — *is the server actually solid, or does
it only look solid between restarts?* — with counts rather than impressions. It is **not** a promotion
gate: nothing was changed, nothing was tuned, and no configuration decision depends on it. The engine
under test is the one that went into production at 19:46 local the same day
([`gates/xgrammar-backports-11sep.md`](gates/xgrammar-backports-11sep.md)), untouched.

**Scope and honesty about it.** The load is synthetic and generated by this repository's own
instruments. A 90-minute window does not speak for a week, and the shapes exercised are the shapes we
know how to exercise — agentic tool loops, long prose turns, one- and multi-image requests, short code.
The §7 list says what this run does *not* establish, and it is longer than the results.

---

## 1. Settings

Three DGX Spark (GB10, sm\_121) nodes over the ConnectX-7 mesh, image `exl3-zeus:754421f`
(vLLM `0.1.dev20051+g487ecf187`), checkpoint `turboderp/GLM-5.3-Flash-exl3` branch `4.05bpw`
(full scope), **TP=3 + expert parallelism**, DFlash2 draft at k=7 with an fp8 draft cache, KV dtype
fp8, `gpu-memory-utilization` **0.88**, `max-model-len` **1,000,000**, `--block-size 256`,
`--max-num-batched-tokens 2048`, `--max-num-seqs 8`, `enforce_eager`, vision tower on
(`--limit-mm-per-prompt {"image":4,"video":2}`), `HAREM_KDA_FLASHKDA=1`, `HAREM_PREFIX_HIT=1`,
`HAREM_KPOOL_TAIL_FIX=1`, `HAREM_GLM47_FAILCLOSED=1` with the `required` arm on,
`HAREM_XGRAMMAR_BACKPORT=1`, `HAREM_SM12_ITEMS=pdl,kpool`, `HAREM_INDEXER_WS_MODE=bound`,
`clear_thinking: true`, `reasoning_effort: low` as the production default. Fast-load sidecar
`/var/tmp/glm53-exl3-xgrammar-r{0,1,2}` in `load` mode; the boot's KV pool was **7,030,303 tokens**.
Engine port 8001, `harem-exl3.service` enabled on all three nodes.

**The engine was shared.** It serves Hermes as well, so the soak held its own concurrency at **2** and
watched `vllm:num_requests_waiting`, ready to drop to 1. It never had to: waiting stayed at 0 for the
whole window, and `num_requests_running` peaked at 4 — inside `max_num_seqs` 8 with room left. Every
number below that comes off `/metrics` or the engine log therefore counts **all** clients, not only
the soak; the per-request tables count only the soak's own requests, and each table says which it is.

**Nothing was written to the production nodes.** Node-side evidence is read-only
`sudo -n docker logs`, `nvidia-smi`, `free`, `ibv_devinfo` and `journalctl`.

## 3. The soak — 20:46 to 22:15 local, 89 minutes of continuous load

**Two honest disclosures first.** (1) The driver was restarted once, at 20:52, because the A/B in §4
had been built wrong; run 1's 30 tool-call turns are kept and counted, its 5 text answers are counted
in the totals but excluded from the §4 pair. (2) The driver's tail had no loop guard, so in the last
~2 minutes it spun through ~100 vision-only cycles. That is why vision has 114 samples rather than 12,
and why the last two minutes of the window are vision-heavy. Nothing was lost; the distribution is
simply not uniform, and the vision count should be read as "114 requests, of which ~100 in a 2-minute
burst".

### 3.2 The strict tool-call gate, fourteen runs

Each run is 2 sessions × 15 rounds, concurrency 2, `--max-prompt-tokens 120000`, effort low, through
the strict proxy — the same protocol as the 19:25 gate at a fifth of the size, repeated every cycle.

| | total across 14 runs |
|---|---|
| turns | **420** |
| tool calls | **493** |
| well-formed | **493** |
| rejected by the fail-closed parser | **0** |
| schema violation | **0** |
| JSON error | **0** |
| empty turn | **0** |
| `finish_reason: length` | **0** |

| turns the gate counts as corrupt | **0** |
| identical repeat of the previous call | **4** |
| deepest prompt seen | **96,552 tokens** |

**The one blemish in the whole soak is that `4`.** In cycle 10, session 0, turns 12–15 emitted a
byte-identical `read` call four times running, at 14,692 → 17,008 prompt tokens. All four were
well-formed; the gate's `corrupt` definition deliberately excludes repeats
(`corrupt = rejected or schema_viol or json_err or empty_turn`), so this is the model looping in the
agent loop, not the engine emitting bad output. It broke out by itself on turn 16 and no other cycle
showed it.

It is worth saying what this is **not**: it is not the deep-context loop issue #7 predicts at ~71 k.
It happened at 15 k, and the turns we actually ran above 70 k — three in cycle 6 (to 96,552) and three
in cycle 10 and 12 (to 77,210 and 76,508) — were clean. One loop episode in 420 turns, at shallow
depth, is a reason for a repeat-breaker on the agent side, which Hermes already has.

### 5.1 Speed — NOT VERIFIED tonight, and why

Every speed reading came back low, and they must not be published as measurements:

| | this run | baseline | |
|---|---|---|---|
| C1 aggregate | 32.38 tok/s | 69.9 (7 Sep, production 12 arm A) | −54 % |
| C1 per-stream | 39.93 | 73.64 | −46 % |
| C8 aggregate | 164.7 | 195.78 | −16 % |
| single-stream decode, 512 tokens, median of 3 | 42.18, then 31.16 on a retry | 61.28 (10 Sep, same instrument) | −31 % / −49 % |
| TTFT, fresh ~7 k prompt, median of 5 | 4.793 s | 3.978 s | +20 % |
| sustained prefill, 60 s window, conc 24 | 1,758.5 tok/s | 1,867.4 / 1,868.8 | −5.8 % |
| spec-decode acceptance at C1 | 42.9 %, length 3.87 | 62.08 %, 5.35 | −31 % |

**The engine was never quiet.** Hermes held a request in flight through the whole block; the idle check
before the decode run read `running=1`, the retry caught `running=0` at 22:42:35 and Hermes was back by
the time it finished. The readings behave exactly as contention behaves and not as a regression does:

- the three decode reps *degraded monotonically* — 45.4, 42.18, 31.28 — inside 40 seconds, and the
  retry's three reps were 14.8, 46.66, 31.16, a 3× spread on an unchanged engine;
- the five TTFT samples rose monotonically, 4.223 → 5.672;
- C1 per-stream 39.93 is almost exactly the **C4** baseline (41.83), which is what "my 1 stream plus
  three of someone else's" should read.

**And the engine demonstrably is not slow.** The soak's own short-code phase is 54 single-shot
~150-token generations spread across the full 89 minutes: **p50 64.9 tok/s, max 82.2, and 32 of 54
above 60** — at or above the 61.28 baseline, measured over an hour and a half rather than 40 seconds.
`HAREM_FLASHKDA` is confirmed live in this boot's log
(`kda_prefill_backend=flashkda (HAREM_KDA_FLASHKDA='1')`), so the 1,758 prefill reading is not a lost
patch, and no node reported a throttle flag.

So: **no evidence of a speed regression, and no band check passed either.** The speed block has to be
re-run on a quiet engine before any number from it is quoted. One thing in the soak data does deserve
that re-run's attention: those 54 code generations trend down across the window (21:00 read
82 / 75 / 73, 22:13 read 64 / 60 / 57), which is confounded with both Hermes load and a 30 °C
temperature rise and is resolved by neither `[not measured]`.

Read-only, from the service journal and unit configuration; no failure was induced.

| | measured |

| clean stops (`Deactivated successfully`) | **47** — every one a stop we issued |
| `Failed with result` | **1** |
| what that one was | 10 Sep 06:26:29, a **refused start**: `fastload sidecar yok: /var/tmp/glm53-exl3-flashkda-r0`, the preflight correctly refusing a `load` boot with no sidecar |
| unplanned exits of a *running* engine | **0** |
| `harem-exl3.service` | `enabled` + `active` on all three nodes |
| `ibv_devinfo` PORT_ACTIVE | **4/4 on all three** |
| container restarts (`docker inspect .RestartCount`) | **0** |
| node uptime | 13 h 17 m |

**The open risk.** The unit carries `Restart=no` and the container `RestartPolicy=no`, so if the engine
dies nothing brings it back — a human does. That is arguably correct rather than broken: restarting one
node alone kills the fabric port on its peers, so any automatic recovery here has to turn all three
together, and a naive per-unit `Restart=on-failure` would make things worse, not better. It is a design
decision to take deliberately, not a gap to paper over.

## 4. The think-channel pair, and why it is a controlled pair

Issue #7's second finding is that under an active structural tag `<think>` and `</think>` land in the
tag's excludes; the GLM template opens thinking unconditionally, so the model cannot close it, and a
think→**text** turn then either skips reasoning or spills the plan into `content`. think→tool-call is
unaffected because the parser closes at `<tool_call>`.

Two things make this testable here rather than hypothetical:

1. **The precondition is present on our engine.** The boot's own config line reads
   `structured_outputs_config=StructuredOutputsConfig(backend='auto', …, reasoning_parser='deepseek_r1',
   …, enable_in_reasoning=False)`. That `False` is the knob the report is about.
2. **One variable separates the arms.** On this engine a structural tag is built only when some tool
   carries `strict: true` — `_any_tool_strict` with `tool_choice: "auto"` and no strict tool returns
   `None` from `get_model_structural_tag` (read out of our own image, 11 September 16:22). So:

| arm | tools attached | `strict` injected | grammar |
|---|---|---|---|
| `strict` | yes | yes, by `strict-proxy.py` | **on** |
| `plain` | **the same tools** | no | off |
| `notools` | no | no | off |

The first attempt at this pair was thrown away and the driver restarted at 20:52, because the `plain`
arm had been sent *without* tools — which moves two variables at once and would have measured nothing.
The `notools` arm is kept deliberately, one prompt per cycle, so "tools present" and "grammar on" stay
separable. Each cycle sends the same prompt down all arms at the same time, at
`reasoning_effort: high` with a 3,000-token ceiling, and records per answer: `finish_reason`,
`len(content)`, `len(reasoning_content)`, and whether a literal `<think>`/`</think>` survived into
`content`. A healthy turn is non-empty `content` **and** non-empty `reasoning_content` — which
together are the evidence that the channel opened and closed.

### 4.1 The result: the symptom did not reproduce

Over the soak, every arm answered cleanly, and `strict` and `plain` are indistinguishable:

| arm | answers | ok | empty `content` | `reasoning_content` empty | literal `<think>`/`</think>` in `content` | median reasoning chars | median content chars |
|---|---|---|---|---|---|---|---|
| `strict` (grammar **on**) | 29 | **29** | **0** | **0** | **0** | 161 | 6,120 |
| `plain` (same tools, grammar off) | 29 | **29** | **0** | **0** | **0** | 161 | 6,017 |
| `notools` (grammar off) | 13 | **13** | **0** | **0** | **0** | 314 | 6,096 |

The dedicated three-arm run afterwards, which keeps the text
(`regression/think-channel.json`), says the same thing on one prompt at effort high with a 2,500-token
ceiling: `finish_reason: stop` in all three, zero tool calls, reasoning 77 / 77 / 130 characters,
content 2,890 / 3,697 / 4,173 characters, no tag leak anywhere.

**Reading it.** The median reasoning length is *identical* at 161 characters with grammar on and off,
while the no-tools arm reasons about twice as long (314). So on this build, attaching tools shortens
reasoning and **turning grammar on does not change it at all** — which is the opposite of the reported
symptom, where grammar should have suppressed the reasoning channel or spilled it into `content`.
Neither happened once in 71 answers.

This is a **negative result, not an all-clear** (§7). The precondition is present in our config, the
sample is a few dozen turns at one effort setting on one image, and a rare case survives this easily.
What it does establish is that the symptom is not a routine occurrence on our production engine.


## 7. What this run does not establish

- **Ninety minutes is not a week.** Nothing here speaks to a multi-day leak, to thermal drift over a
  long session, or to anything that needs more than one boot to appear. The one long-horizon claim in
  §6 comes from the service journal, not from this window.
- **The load is synthetic and ours.** It exercises the shapes this repository knows how to generate.
  Real Hermes traffic ran alongside it, which is realistic, but it also means the engine-side counters
  in §5 mix two clients and cannot be attributed to the soak alone.
- **Concurrency was held at 2 on purpose**, because the engine is shared. Nothing here tests the
  engine at its `max_num_seqs` ceiling under sustained pressure; the only high-concurrency moments
  were the two 60-second prefill windows and the C6/C8 levels of the sweep, which are short by design.
- **No quantisation-quality claim.** `correctness-probe` and `code-exam` were *not* re-run here — they
  passed at 19:28 on this exact boot and nothing in between could move them `[not tested]`. MMLU,
  ExtractBench and the full 1 M needle suite were not run `[not tested]`.
- **The think-channel result is a negative, on one build, at one effort setting.** It says the symptom
  reported in issue #7 did not reproduce on our engine in this window. It does not say the upstream
  mechanism is absent — the precondition (`enable_in_reasoning=False`) *is* present in our config, and
  a negative over a few dozen turns cannot rule out a rare case.
- **Grammar-on has no positive marker in the log any more.** Before the backports, a strict window
  announced itself with a burst of FSM errors, which is how we knew the grammar path was live. With
  the backports that burst is gone — which is the point of them, but it also means "grammar was
  active in the strict arm" now rests on the 16:22 code reading plus the 16:32 error burst from the
  identical proxy-and-gate setup, not on a marker inside this run.
- **Speed numbers taken on a shared engine.** The idle check before each speed measurement is
  recorded, but Hermes could have issued a request mid-window without the check seeing it. Treat the
  speed block as a band check against the declared tolerances, not as a new published figure.
- **No fault injection.** Nothing was killed, starved, unplugged or filled up. "It did not fall over"
  here means "it was not pushed over", and the recovery path in §6 is read from configuration, not
  from an induced failure `[not tested]`.
